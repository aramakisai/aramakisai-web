# Requirements Document

## Project Description (Input)
学生団体が迷わず自分の企画だけを入稿できるよう、Payload の admin UI 側を制御する。
API レベルの access control (cms/src/access/policy.ts) は実装済みだが、管理画面の表示制御は別途必要。

やること:
- 他団体の企画が一覧に出ないようにする (現状 owner フィルタで編集は不可だが、公開済みのものは閲覧可)
- 出展者に関係のないコレクションを admin UI から隠す (sponsors / map_areas / pages / faq_items / stages など)
- 実行委員が決めた割当 (エリア、ステージの時間枠など) を入れた受け皿レコードを、該当する団体ユーザーに付与できるかを確認する。可能なら実行委員側の運用手順も決める
- 入稿画面の項目が出展者から見て自明かを確認し、ラベルや説明文を調整する
- 自分がオーナーでないメディアの閲覧制限

前提: student_exhibitor ロールが作成できるのは student_exhibitions と media のみ。認証は荒牧祭SSO (Zitadel、OIDC) (ローカル認証は実行委員の緊急用)。
アカウント一括発行 (10/1-10/3) より前に完了している必要がある。期日 2026-09-28。
リポジトリ: cms

## Introduction
学生団体 (`student_exhibitor` ロール) が Payload 管理画面にログインしたとき、次の状態にする。

- 自分の企画と自分のメディアだけが見える
- 実行委員が決めた割当は変更できない
- 入稿した内容は、実行委員が確認して公開状態にしたときにはじめて公開サイトに出る
- 入稿項目の意味が画面上の説明だけで分かる

出展者アカウントは荒牧祭SSO (OIDC) を経由させない。Payload のローカル認証 (email/password) アカウントとして発行し、作成と同時に、パスワード設定リンクを含む招待メールを自動送付する。

ローカル認証を採るのは、アカウント一括発行をスクリプトで行いやすいためである。Payload の API だけで、次の 2 つを完結できる。

- ユーザーの作成
- owner・エリア・ブース番号を入れた企画レコードの作成

API レベルの行レベル access control (`cms/src/access/policy.ts`) は「編集は owner 一致のみ」を満たしている。しかし読み取りは公開状態に従うため、他団体の公開済み企画と全メディアが管理画面に出る。出展者に無関係なコレクションもナビゲーションに並ぶ。公開状態も出展者自身が切り替えられる。

全ての要件の期日は 2026-09-28 (アカウント一括発行 2026-10-01〜10-03 の前) とする。

### 現行コードから確認した前提
- `student_exhibitions.owner` の現状:
  - `unique` (1 ユーザー 1 企画) で、`admin.hidden: true` のため実行委員の画面にも出ない。
  - `beforeChange` はリクエストのユーザーが実行委員のときだけ指定値を採る。それ以外は既存値か `req.user.id` を入れる。
  - このため現状の管理画面から実行委員が作った企画は実行委員本人の所有になり、実行委員 1 人につき 1 件しか作れない。
  - Local API で `user` を渡さずに作成すると、`req.user` が無いため指定した owner が捨てられ、必須違反になる。
- `student_exhibitions.status` (公開 / 下書き) は出展者も自由に変更できる。`公開` にした時点で未認証 REST (公開サイト) に返る。承認の段階は存在しない。
- 割当に当たる項目は次の 2 系統。
  - `student_exhibitions` の `area_id` (マップ配置エリア) / `booth_number` (ブース番号) / `booth_label` (マップ表示ラベル)。いずれもフィールド単位の制限がなく、出展者が書き換えられる。
  - `performance_slots` (ステージ出演枠)。実行委員のみ作成でき、企画側では join で閲覧のみ。
- `media` の現状:
  - 所有者を表すフィールドを持たない。
  - 読み取りは未認証を含め全件許可。更新・削除は実行委員のみ。
  - 配信エンドポイント `/api/media/serve/:id/:size` (`cms/src/collections/media.ts`) は `findByID` を `overrideAccess: false` なしで呼ぶ。このため read access を絞っても素通りする。
- `users` は `auth: true` で、ローカル認証はロールを問わず有効。ただし出展者は `users` の read/update が全て拒否されている (`PRIVATE_COLLECTIONS`)。このため自分のアカウント画面とパスワード変更が使えない。
- 現行の IdP は荒牧祭SSO である。コード上の識別子 (`authentikEndpoints`、`AUTHENTIK_ISSUER_URL`、`authentik_sub` 等) は旧名のまま残っている。OIDC ログイン (`cms/src/auth/authentik-endpoints.ts`) の挙動:
  - OIDC のグループ `student_exhibitor` を出展者ロールへ写像する (`cms/src/auth/role-mapping.ts`)。
  - `authentik_sub` で引けないときは `email` で既存ユーザーを引き当て、sub・ロールを上書きする。
  - このため、ローカル発行した出展者アカウントと同じメールアドレスの荒牧祭SSO ユーザーが OIDC でログインすると、そのアカウントに紐づき、ロールも書き換わる。
- メール送信経路の現状と方針:
  - 現状、`payload.config.ts` に email adapter は無い。
  - 本 spec では Payload に email adapter を入れ、クラスタ内の docker-mailserver (`aramakisai-infra` の `gitops/manifests/prod/mailserver`) に送信専用アカウント `noreply@aramakisai.com` で SMTP 接続する。
  - 送信専用アカウントのパスワードは Infisical の `NOREPLY_SMTP_PASSWORD` にある。ただし現行の `cms-secrets` の ExternalSecret (`gitops/manifests/prod/cms-secrets/external-secret.yaml`) には含まれていない。
  - 同じアカウントでの送信は vaultwarden が既に行っている (submission 587 / STARTTLS)。
- アクセス判定は管理画面と REST で同じ関数を通る。フロントエンドは未認証 REST で読み、公開判定に `status=published` を直接使う。

## Boundary Context
- **In scope**:
  - 出展者ロールから見た管理画面の表示範囲 (一覧・ナビゲーション・メディア)
  - 割当の受け皿レコード方式の決定と実現
  - 出展者ローカルアカウントの発行と招待メールの自動送付・再送
  - 出展者の OIDC からの切り離し
  - 公開の承認制 (公開状態は実行委員だけが変更し、出展者は下書きの自分の企画だけを編集する)
  - 出展者による自メディアの更新・削除
  - 出展者向けラベル・説明文
  - 実行委員の運用手順
- **Out of scope**:
  - 一括発行スクリプト自体。WBS アイテム「学生団体アカウント一括発行」の成果物であり、本 spec はそのスクリプトが Payload の API だけで発行を完結できる状態を用意するところまでを担う
  - 学生団体向け入稿手順書そのもの (本 spec の完了後に別途作成する)
  - 実行委員アカウントの発行方法 (従来どおり荒牧祭SSO の OIDC)
  - フロントエンド (`frontend/`) の変更
- **Design で決める事項**:
  - 出展者による公開状態の変更と、公開済み企画の保存を拒否する実現手段
  - 公開された企画から参照されているメディアを判定する実現手段
  - 再設定リンクの具体的な有効期限 (招待リンクの有効期限は要件 4.8 のとおり発行から 72 時間)
  - 問い合わせ先を持つ設定値の置き場所
  - 招待メールの組み立て方。参考情報:
    - Payload 3.88 の `payload.forgotPassword({ disableEmail: true, expiration })` はトークンを返す。これを使えば招待メールを再設定メールとは別に組み立て、`payload.sendEmail` で送れる。
    - 呼び出しごとの `expiration` が効くのは、collection 設定の `auth.forgotPassword.expiration` が未設定のときだけ (collection 設定が優先される)。
    - `expiration` はミリ秒の相対値である。招待リンクには 72 時間分のミリ秒を渡す。
- **Adjacent expectations**:
  - 実行委員ロールの見え方・操作範囲は、owner 選択と招待メール再送の追加を除き変わらない。
  - 実行委員がアップロードしたメディアと公開状態の企画は、公開サイトから従来どおり読める。
  - スキーマ変更は追加のみとし、`cms-schema-check.yml` の破壊的変更検出に掛からない形で入れる。
  - SMTP 資格情報を CMS の Pod に渡すため、`aramakisai-infra` 側で `cms-secrets` に `NOREPLY_SMTP_PASSWORD` を追加する変更が要る。

## Requirements

### Requirement 1: 他団体の企画を出展者に見せない
**Objective:** As a 学生団体の担当者, I want 管理画面の学生企画一覧に自分の企画だけが出ること, so that 他団体の企画を誤って開いたり編集しようとして迷わない

#### Acceptance Criteria
1. While 出展者ロールでログインしている, the CMS shall 学生企画の一覧・検索・件数に owner が自分であるレコードだけを含める
2. If 出展者が他団体の学生企画の ID を直接指定して、詳細画面または REST で読み取ろうとした, the CMS shall そのレコードの内容を返さない
3. While 実行委員ロールでログインしている, the CMS shall 全ての学生企画を一覧・編集可能なまま保つ

### Requirement 2: 出展者に無関係なコレクション・グローバルを管理画面から隠す
**Objective:** As a 学生団体の担当者, I want 管理画面のナビゲーションとダッシュボードに入稿に必要なものだけが並ぶこと, so that どこを触ればよいか迷わない

#### Acceptance Criteria
1. While 出展者ロールでログインしている, the CMS shall ナビゲーションとダッシュボードに学生企画とメディアだけを表示する
2. While 出展者ロールでログインしている, the CMS shall 次のコレクションとグローバルをナビゲーションとダッシュボードに表示しない
   - コレクション: ユーザー・お知らせ・トピック・固定ページ・協賛企業・FAQ・マップエリア・ステージ・タイムスロット・ステージ出演枠
   - グローバル: 祭メタ情報・トップページ
3. While 出展者ロールでログインしている, the CMS shall 自分の学生企画の詳細画面で、割り当てられたマップ配置エリア・ステージ出演枠の表示名を従来どおり解決して表示する
4. While 実行委員ロールでログインしている, the CMS shall 全てのコレクションとグローバルをナビゲーションに表示する

### Requirement 3: 割当済み受け皿レコードの付与 (方式1 の採用)
**Objective:** As a 実行委員, I want 割当を入れた学生企画レコードを先に作り、該当団体のユーザーを所有者に設定して渡せること, so that 割当が団体の入稿開始より前に確定し、団体は割当を前提に入稿できる

割当はエリア・ブース番号・ステージ出演枠を指す。割当方式は方式1 (実行委員が受け皿レコードを先に作り、owner に団体ユーザーを設定する) を採る。方式2 (団体が先に作り、後から割当を編集する) は割当確定が団体の入稿より後ろにずれ、WBS の期日と両立しないため採らない。

エリアとブース番号は実行委員が管理する項目であり、出展者には編集させない。

#### Acceptance Criteria
1. While 実行委員ロールでログインしている, the CMS shall 学生企画の作成・編集画面で所有者 (owner) を出展者ロールのユーザーから選択できるようにする
2. When 実行委員が所有者・マップ配置エリア・ブース番号を指定して学生企画を作成した, the CMS shall 指定されたとおりの値で保存する
3. The CMS shall 3.2 の作成を、管理画面・REST・Local API のどの経路で行っても同じ振る舞い (同じ値の保存・同じ検証・同じエラー) にする
4. If 既に別の学生企画の所有者であるユーザーを所有者に指定して保存した, the CMS shall 保存を拒否し、どのユーザーが重複しているかを示すメッセージを返す
5. When 所有者に設定されたユーザーが出展者ロールでログインした, the CMS shall そのレコードを自分の学生企画として一覧に表示し、下書き状態のあいだ編集可能にする (要件 7)
6. While 出展者ロールでログインしている, the CMS shall 所有者を表示も変更もさせない
7. While 出展者ロールでログインしている, the CMS shall マップ配置エリアとブース番号を読み取り専用で表示する
8. If 出展者がマップ配置エリアまたはブース番号を変更する保存を行った (管理画面・REST を問わない), the CMS shall その変更を反映しない
9. While 出展者ロールでログインしている, the CMS shall マップ表示ラベルとステージ出演枠を読み取り専用で表示し、これらの値を変更する保存を受け付けない
10. The CMS shall 出展者ロールのユーザーによる学生企画の新規作成を、管理画面・REST を問わず受け付けず、管理画面に新規作成操作を提示しない

### Requirement 4: 出展者ローカルアカウントの発行
**Objective:** As a 実行委員, I want 出展者アカウントを Payload のローカル認証アカウントとして発行し、招待メールを自動送付できること, so that 出展者に他アプリ用の IdP アカウントを作らず、一括発行スクリプトでも同じ手順で入稿を始めてもらえる

招待リンクの有効期限は、発行 (再送を含む) から 72 時間の固定値とする。

#### Acceptance Criteria
1. The CMS shall メールアドレスを指定して、出展者ロールのローカル認証アカウントを作成できるようにする
2. When 出展者ロールのアカウントが作成された, the CMS shall そのアカウントのメールアドレス宛に招待メールを自動送付する
3. The CMS shall 招待メールの件名と本文をアカウント発行の案内とし、パスワード再設定メールとは別の文面にする
4. The CMS shall 招待メールに次を含める
   - CMS の用途 (荒牧祭の出展情報の入稿に使うこと)
   - ログイン URL
   - パスワード設定リンク
   - 問い合わせ先
5. The CMS shall 4.1 の作成と 4.2 の招待メール自動送付を、管理画面・REST・Local API のどの経路で作成しても同じように行う
6. The CMS shall 出展者宛のメールに平文のパスワードを含めない
7. The CMS shall 送信元を送信専用アカウント (`noreply@aramakisai.com`) とし、クラスタ内の docker-mailserver への SMTP 接続で送信する
8. The CMS shall 招待メールのパスワード設定リンクの有効期限を、発行 (再送を含む) から 72 時間とする
9. The CMS shall 招待メールの問い合わせ先をコードに直書きせず、デプロイ時の設定値として与える
10. If 招待メールの送信に失敗した, the CMS shall アカウント作成を取り消さず、失敗を実行委員が識別できる形で記録する
11. While 実行委員ロールでログインしている, the CMS shall 出展者アカウントを指定して招待メールを再送できるようにする (有効期限切れ・送信失敗・紛失のいずれの場合も)
12. When 招待メールが再送された, the CMS shall 新しい有効期限のパスワード設定リンクを発行し、以前に送った招待リンクを無効にする
13. When 出展者が招待リンクからパスワードを設定した, the CMS shall そのパスワードでのログインを出展者ロールとして受け付け、管理画面を表示する
14. If 出展者が有効期限切れの招待リンクを開いた, the CMS shall パスワードを設定させず、実行委員へ再送を依頼するよう示す
15. When 出展者がログイン画面からパスワード再設定を要求した, the CMS shall そのアカウントのメールアドレス宛にパスワード再設定メールを送付する
16. The CMS shall パスワード再設定メールを、ログイン画面から本人が要求したときにだけ送付する
17. While 出展者ロールでログインしている, the CMS shall 自分のパスワードを変更できるようにする
18. If 出展者ロールのユーザーが、自分または他人のアカウントのロール・メールアドレス・OIDC 識別子を変更しようとした, the CMS shall 拒否する
19. If 出展者ロールのユーザーがユーザーの作成を行おうとした, the CMS shall 拒否する

### Requirement 5: 出展者を OIDC ログインから切り離す
**Objective:** As a 実行委員, I want 出展者ロールがローカル認証アカウントからしか生じないこと, so that IdP 側のグループ設定やメールアドレスの一致で、出展者の権限・アカウントが意図せず変わらない

#### Acceptance Criteria
1. When 荒牧祭SSO (OIDC) ログインで、利用者のグループが出展者に相当するものだけだった, the CMS shall セッションを確立せず、ログインを拒否する
2. The CMS shall 荒牧祭SSO (OIDC) ログインによって出展者ロールのユーザーを新規作成しない
3. When 実行委員の荒牧祭SSO (OIDC) ログインで得たメールアドレスが既存の出展者アカウントと一致した, the CMS shall そのアカウントに OIDC の識別子を紐づけてロールを実行委員にし、同時にローカル認証のパスワードを推測できない値に差し替え、今回のログイン以外の既存セッションを全て無効にする (実行委員が入稿者を兼ねる可能性があるため拒否はしない。出展者に伝わっていたパスワードで実行委員の権限を得られないようにする)
4. The CMS shall 実行委員の荒牧祭SSO (OIDC) ログインを従来どおり受け付ける

### Requirement 6: 実行委員の運用手順
**Objective:** As a 実行委員, I want アカウント発行から団体への引き渡し、公開までの手順が文書化されていること, so that 誰が担当しても同じ手順で準備・公開できる

#### Acceptance Criteria
1. The 運用手順書 (`docs/cms-operations.md`) shall 出展者ローカルアカウントの発行と、招待メールの自動送付と、有効期限切れ・送信失敗時の再送の手順を記載する
2. The 運用手順書 shall 受け皿レコードの作成・所有者設定・エリア/ブース割当・ステージ出演枠作成の順序を、管理画面と API の双方について記載する
3. The 運用手順書 shall 出展者本人によるパスワード再設定の流れを記載する
4. The 運用手順書 shall 出展者から見た操作範囲 (見える項目・編集できる項目・公開までの流れ) を記載する
5. The 運用手順書 shall 下書きの企画を確認して公開状態にする手順を記載する
6. The 運用手順書 shall 公開後に出展者が修正を求めた場合に、実行委員が企画を下書きに戻して出展者に編集させ、修正後に再び公開する手順を記載する
7. The 運用手順書 shall 公開前の確認で修正が必要な場合に、出展者へ修正を依頼する連絡手段 (システム外) を記載する

### Requirement 7: 公開の承認制
**Objective:** As a 実行委員, I want 出展者の入稿内容が実行委員の確認を経てからしか公開サイトに出ず、公開後に出展者が内容を変えられないこと, so that 不適切・誤りのある内容が監査なしに公開されない

公開状態は「下書き」「公開」の 2 状態とする。差し戻しはシステムで持たず、運用でカバーする (要件 6)。

#### Acceptance Criteria
1. The CMS shall 学生企画の公開状態を「下書き」「公開」の 2 状態とする
2. While 出展者ロールでログインしている, the CMS shall 学生企画の公開状態を変更する操作を提供しない
3. If 出展者が学生企画の公開状態を変更する保存を行った (管理画面・REST を問わない), the CMS shall その変更を反映しない
4. While 学生企画が下書き状態である, the CMS shall 所有者の出展者に編集を許可する
5. If 出展者が公開状態の学生企画を保存しようとした (管理画面・REST を問わない), the CMS shall 保存を拒否し、修正は実行委員へ依頼するよう示す
6. While 学生企画が下書き状態である, the CMS shall 未認証リクエストにその企画を返さない
7. While 実行委員ロールでログインしている, the CMS shall 学生企画の公開状態を「下書き」「公開」のどちらへも変更できるようにする
8. While 実行委員ロールでログインしている, the CMS shall 管理画面の学生企画一覧を公開状態で絞り込めるようにする
9. The CMS shall 出展者がアップロードし、公開状態の学生企画から参照されていないメディアを、未認証リクエスト (配信エンドポイント `/api/media/serve/:id/:size` を含む) に返さない
10. When 実行委員が学生企画を公開状態にした, the CMS shall その企画から参照される出展者アップロードのメディアを、未認証リクエストに返す状態にする
11. The CMS shall 配信エンドポイント `/api/media/serve/:id/:size` で、リクエスト元の read access を評価してから配信先を返す
12. While 出展者ロールでログインしている, the CMS shall 自分の企画が下書きか公開かを判別できるように表示する

### Requirement 8: 出展者が自明に入稿できるラベル・説明文
**Objective:** As a 学生団体の担当者, I want 入稿画面の各項目の意味と入力方法が画面上の文言だけで分かること, so that 手順書や実行委員への問い合わせなしに入稿できる

#### Acceptance Criteria
1. The CMS shall 出展者に表示される学生企画・メディアの項目ラベルと説明文に、DB 用語やフィールド名 (NULL、UNIQUE、NOT NULL、`area_id` 等) を含めない
2. The CMS shall 出展者の画面で、入稿内容は実行委員が公開して初めて公式サイトに掲載されることを示す
3. The CMS shall 出展者の画面で、公開状態の企画は編集できず、修正は実行委員へ依頼することを示す
4. The CMS shall 割当項目 (エリア・ブース番号・マップ表示ラベル・ステージ出演枠) の説明文で、実行委員が設定する項目であり、変更は実行委員へ依頼することを示す
5. The CMS shall 画像項目とメディアの代替テキストの説明文で、次を示す
   - 用途 (サイト上のどこに表示されるか)
   - 代替テキストは画像を説明する文であること
   - 枚数上限
   - 公開中の企画で使っている画像は変更・削除できないこと
6. The CMS shall 各カテゴリの企画内容 (企画名・紹介文・画像) の説明文で、公式サイトのどこに表示されるかを示す

### Requirement 9: 出展者のメディアを本人に限定する
**Objective:** As a 学生団体の担当者, I want メディア一覧と画像選択ダイアログに自分がアップロードした画像だけが出て、未公開のものは自分で差し替え・削除できること, so that 他団体・実行委員の画像を誤って使わず、公開済みの画像を壊さずに自分の画像を管理できる

本要件で「承認済みのメディア」は、公開状態の学生企画の内容から参照されているメディアを指す。企画が下書きに戻されると、そのメディアは承認済みでなくなる。

#### Acceptance Criteria
1. When 利用者がメディアをアップロードした, the CMS shall そのメディアにアップロードしたユーザーを所有者として記録する
2. While 出展者ロールでログインしている, the CMS shall メディア一覧・画像選択ダイアログ・件数に、自分が所有者のメディアだけを含める
3. If 出展者が自分が所有者でないメディアの ID を直接指定して読み取ろうとした, the CMS shall そのメディアの内容を返さない
4. While 出展者ロールでログインしている, the CMS shall 自分が所有者で承認済みでないメディアについて、更新 (代替テキスト・ファイル差し替え) と削除を許可する
5. If 出展者が承認済みのメディアを更新または削除しようとした, the CMS shall 自分が所有者であっても拒否する
6. If 出展者が自分が所有者でないメディアを更新または削除しようとした, the CMS shall 拒否する
7. While 実行委員ロールでログインしている, the CMS shall 全てのメディアを一覧・更新・削除可能なまま保つ
8. The CMS shall 所有者の記録を追加する前から存在するメディアについて、次を満たす
   - 所有者なしとして実行委員のみに一覧させる
   - 未認証リクエストへは従来どおり返す
9. If 出展者が自分が所有者でないメディアを学生企画の画像に新しく指定して保存した (管理画面・REST を問わない), the CMS shall 保存を拒否する

### Requirement 10: 期日と検証
**Objective:** As a 実行委員, I want アカウント一括発行の前に、出展者の見え方と公開の制限が確認済みであること, so that 発行直後に団体から混乱の問い合わせが来ない

#### Acceptance Criteria
1. The CMS shall 全ての受け入れ基準を 2026-09-28 までに本番へ反映できる状態にする
2. The CMS shall 要件 1・3・4・5・7・9 の読み取り・書き込み・公開の制限を、出展者ロール・実行委員ロール・未認証の 3 者について自動テストで検証可能にする。要件 3・4 は API 経由の作成も検証対象に含める
3. The CMS shall スキーマ変更を追加のみに限り、`cms-schema-check.yml` の破壊的変更検出を発生させない
