# Implementation Plan

## 1. 前提確認と棚卸し

- [x] 1.1 本番 Directus のスキーマ適用状況を確認し、実装の前提を確定する
  - 本番の `festival_meta` / `page_home` を公開ロールで参照し、`home_active_variant`・`admission_fee`・`payment_note`・`parking_capacity` が残存しているか、`hero_images` が読み取れるかを記録する
  - `sitemap-schema-review` spec の `snapshot.yaml` が本番へ適用済みかを判定し、未適用なら適用の先行が必要である旨を spec 内に記録する
  - 作業ブランチが `dev` の内容を全て含んでいることを確認し、遅れている場合は取り込む
  - 確認結果が spec ディレクトリ内に記録され、Phase 1 のデプロイ前提が明文化された状態になる
  - _Requirements: 1.7, 8.2_

- [x] 1.2 静的コンテンツの棚卸しと Directus 投入一覧を作成する
  - `nightly` が導入したハードコード要素を、ヒーロー画像・概要文・開催日程・会場名・マップ URL・テーマ・来場者数・プライバシーポリシー本文・ナビゲーション項目・SNS リンク・お問い合わせ URL・コピーライト・住所連絡先の単位で洗い出す
  - 各要素を「Directus で管理 (既存フィールド)」「Directus で管理 (フィールド追加が必要)」「コードに残す」に振り分け、コードに残すものは理由を併記する
  - Directus 管理とする要素について、投入先の collection とフィールド、値の出所、投入手段 (管理画面 / REST API)、現在の投入状況を一覧化する
  - 一覧ドキュメントが spec ディレクトリに存在し、以降の投入タスクがそれを参照できる状態になる
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 9.1, 9.2_

- [x] 1.3 ヒーロー画像の公開読み取り権限を付与する migration を追加する
  - ローカル Directus (`docker-compose.yaml`) で検証した結果、必要な権限 (`page_home_files` junction と `directus_files` への公開読み取り) は既存の `directus/migrations/20260713B-rbac-public-sponsors-files.js` と `20260718B-rbac-page-home-files.js` (いずれも `sitemap-schema-review` 由来、`nightly` に既にマージ済み) で付与済みであることを確認した。両権限を削除すると `hero_images` が解決できなくなり、再付与すると `directus_files_id` まで取得できることを確認済み (delete-then-insert で冪等、`down` も実装済み)
  - 新規 migration の追加は不要と判断 (既存実装の重複防止)。本番で `FORBIDDEN` になるのは、これら migration が未デプロイなため (`precheck.md` 参照) であり、Phase 1 デプロイ前提の解消と合わせて解決する
  - _Requirements: 3.1, 8.3_

## 2. 表示コンポーネントのデータ供給対応

- [x] 2.1 (P) ヒーロースライドショーを Directus 由来の画像で動作させる
  - コンポーネント内に固定されている画像パスの配列を削除し、表示する画像 URL を外部から受け取る形へ変更する
  - 画像が 0 件のときはセクション自体を描画せず、1 件のときは前後ナビゲーションを表示しない
  - 自動送りの間隔・前後ナビゲーション・`prefers-reduced-motion` への配慮・先頭画像の優先読み込みを、画像の出所によらず維持する
  - 画像 URL を渡すテストで各枚数のケース (0 件 / 1 件 / 複数) の描画結果が検証され、既存のスライドショー動作テストが通る
  - _Requirements: 1.3, 3.1, 3.2, 3.3, 3.4_
  - _Boundary: HeroSection_

- [x] 2.2 (P) About セクションを外部データで描画できるようにする
  - 概要文・開催日程・会場名・キャンパスマップ URL・テーマ情報を外部から受け取る形へ変更し、コンポーネント内の固定文言を除去する
  - 開催日程を `MM月DD日 HH:mm〜HH:mm` の形式で描画する
  - キャンパスマップの埋め込みは、Google Maps の埋め込み URL と判定できる場合にのみ描画する
  - 各ブロックは対応するデータが欠けている場合に個別に非表示となり、セクション全体は描画され続ける
  - 画像表示を Next.js の画像コンポーネントから素の画像要素へ置き換え、アセット URL 生成の共通処理を通す
  - データを渡すテストで、日程の書式・データ欠落時の非表示・不正なマップ URL の除外が検証される
  - _Requirements: 1.4, 1.5, 2.3_
  - _Boundary: AboutSection, home-page-types_

- [x] 2.3 (P) フッターを Directus 連携に戻し、削除された表示要素を復活させる
  - フッターをサーバー側でデータを取得する形へ戻し、SNS リンクを Directus の値から描画する
  - SNS リンクの取得に失敗した場合は該当ブロックのみ非表示とし、フッター全体の描画は維持する
  - `nightly` で削除された住所・連絡先の表示を、刷新後のレイアウトに沿う形で復活させる
  - ナビゲーションから実在しないリンク先を除去し、お知らせは既存のルートを指すようにする
  - SNS 取得成功時・失敗時の双方でフッターが描画されることがテストで検証される
  - _Requirements: 1.3, 5.1, 5.3, 5.4_
  - _Boundary: Footer_

- [x] 2.4 (P) ヘッダーのナビゲーションを実在ルートのみに整理する
  - お知らせのリンク先を既存のお知らせ一覧ルートへ張り替える
  - 未実装のページ (企画一覧・会場案内・協賛企業) に対応する項目を、後続で戻せる形を保ちつつ一時的に取り除く
  - ナビゲーション定義をテストから参照できる形で公開する
  - モバイルメニューの開閉・サブメニュー・現在地表示が整理後も従来どおり動作することがテストで確認される
  - _Requirements: 5.1, 5.2_
  - _Boundary: Header_

## 3. ページの配線と固定ページの統合

- [x] 3.1 トップページを再構成して二重表示を解消する
  - 祭の概要と開催日程を描画していた既存の 2 コンポーネントの直接描画を取りやめ、About セクションに一本化する
  - ヒーロー画像の URL 配列と About セクションに必要な情報を、取得結果からそれぞれのコンポーネントへ渡す
  - Directus への到達に失敗した場合は Directus 由来の領域のみ描画を省き、ページ構造とヘッダー・フッターは維持する
  - 開催日程と祭概要がページ内で 1 度だけ描画されること、および取得失敗時にページが落ちないことがテストで検証される
  - _Depends: 2.1, 2.2_
  - _Requirements: 1.1, 1.2, 1.4_

- [x] 3.2 共通レイアウトからフッターへデータを供給する
  - フッターを非同期のサーバーコンポーネントとして扱うようレイアウト側を調整する
  - フッター内部の表示ヘルパーがクライアント固有の処理に依存していないことを確認する
  - レイアウト経由でフッターが描画され、SNS リンクが Directus の値で表示されることがテストで検証される
  - _Depends: 2.3_
  - _Requirements: 1.3, 5.3_

- [x] 3.3 プライバシーポリシーを Directus 側へ一本化し、About ページを廃止する
  - `nightly` が追加した静的なプライバシーポリシーのルートを、対応するテストとともに削除する
  - フッターのプライバシーポリシーへのリンク先を、汎用固定ページのルートへ揃える
  - 既存の About ルートとそのテストを削除し、ホームページのセクションへ統合する
  - 削除後も祭メタ情報を取得する共通処理と、それを利用する既存コンポーネントは残す
  - 汎用固定ページ経由でプライバシーポリシーが表示され、静的ルートが存在しないことがテストで検証される
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.6_

## 5. Phase 2: スキーマ追加と追加コンテンツの反映

- [ ] 5.1 祭メタ情報へテーマ・会場・外部 URL のフィールドを追加する
  - テーマ語・テーマ画像・テーマ説明文・会場名・キャンパスマップ URL・お問い合わせフォーム URL のフィールドを、いずれも未入力を許容する形でスキーマへ追加する
  - 既存 collection やフィールドの削除・型変更・必須化を行わない
  - スキーマスナップショットに 6 フィールドが追加され、ローカルの Directus へ適用して管理画面から入力できる状態になる
  - _Requirements: 8.1_

- [ ] 5.2 追加フィールドの公開読み取り権限を付与する
  - 公開ポリシーに対し、追加した 6 フィールドとテーマ画像ファイルの読み取り権限を付与する migration を追加する
  - 適用後に権限キャッシュを反映させる手順 (Directus の再起動) を手順として記録する
  - ローカル環境で適用し、公開ロールから追加フィールドが取得できることを確認する
  - _Depends: 5.1_
  - _Requirements: 8.3_

- [ ] 5.3 追加フィールドを取得してページへ供給する
  - ホームページ用のデータ取得処理に追加フィールドの取得とマッピングを組み込む
  - 追加フィールドが未入力のときも取得処理が失敗せず、空の値として扱われる
  - 型定義に緩い型を持ち込まず、追加フィールドが型安全に参照できる状態になる
  - 未入力時と入力済み時の双方のマッピング結果がテストで検証される
  - _Depends: 5.2_
  - _Requirements: 8.4_

- [ ] 5.4 テーマ・会場名・お問い合わせ先を画面へ反映する
  - About セクションのテーマ表示・会場名・キャンパスマップを、コード内の固定値から取得データへ切り替える
  - フッターのお問い合わせリンクを取得データへ切り替え、未設定時はリンクを表示しない
  - 各項目が未設定の場合に該当ブロックのみ非表示となることがテストで検証される
  - _Depends: 5.3_
  - _Requirements: 5.5, 8.4_

- [ ] 5.5 追加フィールドのコンテンツを投入する
  - テーマ語・テーマ説明文・会場名・キャンパスマップ URL・お問い合わせフォーム URL を投入し、テーマのメインビジュアル画像を Directus へ登録して紐づける
  - 投入内容と手段を投入一覧に追記し、API 経由の分はリクエスト定義を残す
  - 本番へ反映する前に開発環境または staging で表示を確認する
  - 投入後、トップページのテーマ領域・会場情報・フッターのお問い合わせリンクが Directus の値で表示される
  - _Depends: 5.4_
  - _Requirements: 9.3, 9.4, 9.5, 9.6_

## 6. アセット整理と品質ゲート

- [ ] 6.1 静的画像を整理し、サイズ上限を強制する
  - Directus 管理へ移したヒーロー画像とテーマのメインビジュアルをリポジトリから削除する
  - 残す画像 (ロゴ・ファビコン等) を配信サイズが小さい形式で保持する
  - コミット時に大きなファイルの追加を止めるチェックを導入し、上限値を設定する
  - リポジトリ内の画像合計が大幅に削減され、上限を超えるファイルを追加しようとするとコミットが失敗する
  - _Depends: 4.1, 5.5_
  - _Requirements: 6.1, 6.2, 6.3_

- [ ] 6.2 Directus 配信画像の転送量を抑える
  - アセット URL の生成処理に画像変換のパラメータ (形式・幅) を付与し、配信サイズを削減する
  - `sitemap-schema-review` spec が同じ処理の変更方針を持つため、実装状況を確認した上で重複しない形で対応する
  - Edge Runtime の制約に反する画像最適化機構を導入しない
  - ヒーロー画像とテーマ画像が変換済みの形式で配信されることを確認する
  - _Depends: 6.1_
  - _Requirements: 6.4_

- [ ] 6.3 ナビゲーションの整合性をテストで担保する
  - アプリケーションのルート定義を走査して実在するルートの一覧を組み立て、ヘッダーとフッターのナビゲーション定義の遷移先と突き合わせる
  - ページ内アンカーは対応するセクションが存在することを確認対象とする
  - 実在しないルートを指す項目を追加するとテストが失敗する状態になる
  - _Depends: 2.3, 2.4_
  - _Requirements: 5.1, 5.2, 7.4_

- [ ] 6.4 全体の回帰確認と統合
  - 変更・追加した全コンポーネントに対応するテストが揃っていること、Directus 取得の成功時と失敗時の双方が検証されていることを確認する
  - 既存 Directus 連携機能 (お知らせ・トピックス・添付ファイル・汎用固定ページ) が退行していないことを確認する
  - 型チェック・静的解析・整形チェック・テスト・ビルドを全て通す
  - プレビュー環境でヒーロー画像・開催日程の単一表示・ナビゲーションのリンク切れ不在を確認した上で、作業ブランチから `dev` への PR を作成する
  - _Depends: 6.1, 6.2, 6.3_
  - _Requirements: 1.1, 1.2, 1.6, 1.8, 7.1, 7.2, 7.3_
