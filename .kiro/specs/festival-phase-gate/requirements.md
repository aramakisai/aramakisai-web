# Requirements Document

## Project Description (Input)

荒牧祭サイトの公開状態を「開催前フェーズ」と「開催中フェーズ」で切り替える機構を導入する。

フェーズ切替は以下の 2 軸が連動する。

- **トップページの差し替え**: 開催前は現行の簡易トップ、開催中は `full-site-design` で作り直す本番トップを表示する
- **サイト全体の公開範囲制御**: 開催前フェーズでは、現行の簡易トップからの導線に存在しないページ (企画一覧・キャンパスマップ・タイムテーブル等) をすべて非公開にする

フェーズは一方通行ではなく、開催終了後ある程度の時間が経過したら開催前フェーズへ戻す運用を想定する。

### 背景

Directus 時代には `festival_meta.home_active_variant` (`pre_event` / `live`) による切替と、dev 環境向けの URL クエリパラメータ `?home_variant=pre_event|live` によるオーバーライドが設計・実装されていた (`.kiro/specs/page-home-friendly-editing/design.md:344`, `requirements.md:64`)。

しかし Payload CMS 移行と `sitemap-schema-review` によるコンテンツモデル見直し (`page_home` + `page_home_live` の 2-singleton → `page_home` 単体、`sitemap-schema-review/design.md:182`) を経て、この切替機構は現行コードベースから完全に消滅している。`frontend/src` / `frontend/e2e` / `cms/src` のいずれにも `home_variant` / `pre_event` の実装は存在せず、`frontend/middleware.ts` も存在しない。

現状トップページ (`frontend/src/app/(site)/page.tsx:10`) はフェーズ分岐を持たず、`getHomePage()` を無条件に呼ぶのみである。

### 本 spec を先行させる意義

`full-site-design` は 13 個の Figma デザイン単位で requirements / design を刻む変則運用を採っている。現状はページを非公開にする手段が存在しないため、各ページは「完成するまでマージできない」か「未完成のまま来場者に公開される」かの二択になる。

公開ゲートを先に用意することで、`full-site-design` の各ページを非公開状態のままマージでき、段階的な開発とデプロイが可能になる。

### 想定する実装方針 (design フェーズで確定させる)

- フェーズをフロントエンドのソースコード内の定数として保持する。CMS にも環境変数にも置かない
- `frontend/middleware.ts` を新設し、開催前フェーズでは許可パス以外へのアクセスを遮断する
- 開発者向けのフェーズ切替手段として Cookie によるオーバーライドを提供する。Cookie は middleware で読み取るためサイト全体に一括で適用され、明示的に切り替えるまで永続する
- 画面左下に開発用のフェーズ切替ボタンを表示する。本番ビルドでは描画されず、来場者には一切見えないこと

### 確定した論点

- **フェーズの保持場所**: フロントエンドのソースコード内の定数とする。CMS にも環境変数にも持たせず、変更は PR のレビューを経る。切替には再デプロイを要するが、切替は年 2 回かつ日程が事前に分かっているため許容する。これによりフェーズ判定が外部 I/O に依存しなくなり、CMS 障害によるフェーズ判定失敗という失敗モード自体が存在しなくなるため、直近値のキャッシュ保持機構も不要になる
- **実行委員による切替**: 行えない。切替は開発者が PR を出して行う
- **非公開ページへのアクセス時の挙動**: 404 を返す。開催前トップへのリダイレクトは採らない
- **トピックス詳細ページの扱い**: 現行トップページから導線があるが、開催前フェーズでは非公開とする
- **sitemap**: 本 spec のスコープに含め、フェーズに連動して収録内容を変える
- **robots**: 本 spec では扱わない。非公開ページが 404 を返す以上、インデックス防止に robots.txt を要さないため (`gap-analysis.md` 2. 参照)
- **トップページの差し替え**: フェーズに連動させる。別軸のフラグは設けない
- **トップページのデザイン**: `full-site-design` が所有する。本 spec は出し分けの機構のみを持つ

### 継続して詰める論点 (design フェーズ)

- 開催前フェーズで公開するページの指定方法 — パスの静的な列挙か、`full-site-design` が所有するナビ定義からの導出か
- 開催前トップにおけるトピックス節の扱い — 節自体を描画しないか、カードをリンクにしないか
- 開発用オーバーライドを本番ビルドから確実に排除する仕組みと、その検証方法
- フェーズ定数を変更したデプロイの完了後、CDN やキャッシュに残る従前フェーズの応答をどう排除するか

## Introduction

荒牧祭サイトは開催時期によって公開すべき範囲が大きく異なる。開催前は告知中心の簡易な構成で足りる一方、開催中は企画一覧・キャンパスマップ・タイムテーブル等の全機能を来場者へ提供する必要がある。

本 spec は、この 2 つの状態を「開催前フェーズ」「開催中フェーズ」として定義し、サイト全体の公開範囲とトップページの表示を単一の定数で一括して切り替える公開ゲートを導入する。あわせて、開発者がソースコードのフェーズ定数を変更することなく双方のフェーズを閲覧できるオーバーライド手段と、その切替 UI を提供する。

現行コードベースにはフェーズ切替機構もページを非公開にする手段も存在しない。このため `full-site-design` が作り直す各ページは「完成するまで main へマージできない」か「未完成のまま来場者に公開される」かの二択になっている。本 spec を先行させることで、開催中フェーズでのみ公開されるページを非公開のまま段階的にマージできるようになる。

フェーズをビルド時に確定する定数としたことで、本番・プレビュー・ローカルのいずれもデプロイ時点のフェーズで動作する。したがって開催中フェーズを事前に確認する手段は開発者向けオーバーライドのみとなり、オーバーライドは本 spec において補助機能ではなく中核の要件である。

## Boundary Context

- **In scope**: フェーズ状態の定義とソースコード内での管理、開催前フェーズにおけるサイト全体の公開範囲制御、非公開ページへの導線の非提示、フェーズに応じたトップページの出し分け、開発者向けフェーズオーバーライドとその永続化、不正なオーバーライド指定の無視、開発用フェーズ切替 UI、非公開ページの外部露出防止、フェーズに連動する sitemap の提供
- **Out of scope**:
  - 開催中フェーズで公開される各ページの内容・デザインそのもの (`full-site-design` および各ページ単位の spec が所有)。開催前・開催中それぞれのトップページの Figma デザインを含む
  - **CMS (`cms/`) 側のコレクション/グローバル定義の変更**。フェーズをソースコードの定数として保持するため、本 spec は CMS のスキーマに一切手を入れない。マイグレーションの生成も `cms-schema-check.yml` の考慮も不要である
  - **実行委員が管理画面からフェーズを切り替える手段**。切替は開発者による PR とデプロイで行う
  - CMS のロール/RBAC 定義の変更
  - 日時に基づく自動フェーズ遷移
  - 来場者向けの開催状況案内 (カウントダウン等)
  - **robots.txt の新規構築**。非公開ページが 404 を返すことで検索エンジンのインデックス対象から外れるため、フェーズゲートの成立に robots.txt を要しない。現状 robots は Next.js 側にも Cloudflare 側にも存在せず (`gap-analysis.md` 2.)、サイト全体の robots ポリシーとして欲しいかどうかは本 spec とは独立した判断である
  - **開催中フェーズでのみ公開されるページの sitemap 収録**。企画一覧・キャンパスマップ・トピックス等の URL は `full-site-design` がページ構成ごと作り直すため、同 spec が収録対象を確定させる (R9-5)
  - **静的アセット (`frontend/public/` 配下) の公開範囲制御**。`images` (148KB) と `map-tiles` (7.1MB) のみを含み、いずれも単体では未公開ページの内容を明かさない。一方これらをゲート配下に置くには全リクエストを Worker 経由にする必要があり、map-tiles の規模に対して配信コストが見合わない。開催前フェーズでもアセットは取得可能なままとする
- **Adjacent expectations**:
  - `full-site-design` は本 spec が提供する公開ゲートを前提として、未完成のページを非公開のままマージできる。同 spec が所有する「ナビ項目定義の一元管理」は本 spec の公開対象一覧 (R2-3) と領域が重なるため、design の Boundary Commitments で所有権を明記する
  - 開催前・開催中それぞれのトップページのデザインは `full-site-design` が所有する。本 spec はフェーズに応じてどちらを表示するかの機構のみを定義し、デザインの内容には踏み込まない
  - `page-home-friendly-editing` (phase: completed) が設計した `festival_meta.home_active_variant` および `page_home_live` は Payload CMS 移行と `sitemap-schema-review` を経て現存しない。本 spec は同等の出し分けを改めて定義するが、フェーズの保持場所は CMS ではなくソースコードとする点で当時の設計とは異なる。トップページ用 global が `page_home` 単体構成である前提 (`sitemap-schema-review` の決定) は引き継ぐ

## Requirements

### Requirement 1: フェーズ状態の定義と管理

**Objective:** As a 開発者, I want サイト全体の公開状態をソースコード内の単一の定数で開催前と開催中に切り替えたい, so that 切替の内容と時期が PR のレビューと git 履歴に残り、意図しない切替が起きない

#### Acceptance Criteria

1. The 荒牧祭サイト shall 「開催前」「開催中」の 2 つのフェーズ状態のみを定義し、常にいずれか一方を現在のフェーズとする
2. The 荒牧祭サイト shall 現在のフェーズを決定する値を、フロントエンドのソースコード内の単一の定数として保持する
3. The 荒牧祭サイト shall フェーズの変更手段をソースコードの変更に限定し、環境変数・CMS の設定値・実行時の操作のいずれによっても変更されないようにする
4. The フェーズ定数の変更 shall PR のレビューを経て main へマージされる経路でのみ行われ、変更内容と変更時期が git 履歴に残る
5. When フェーズ定数を変更したデプロイが完了する, the 荒牧祭サイト shall それ以降のリクエストへ新しいフェーズを適用し、変更前のフェーズの応答を返さない
6. The 荒牧祭サイト shall 開催前から開催中への遷移と開催中から開催前への遷移の双方を、同一の手段 (フェーズ定数の変更) で行えるようにする
7. The 荒牧祭サイト shall 開催後専用のフェーズを設けず、開催終了後は開催前フェーズへ戻す運用で対応する
8. The 荒牧祭サイト shall 日時に基づく自動的なフェーズ遷移を行わない

### Requirement 2: 開催前フェーズにおける公開範囲の制御

**Objective:** As a 実行委員, I want 開催前フェーズでは明示的に許可したページだけを公開したい, so that 制作途中のページが来場者の目に触れない

#### Acceptance Criteria

1. While 現在のフェーズが開催前である, the 荒牧祭サイト shall 公開対象として明示的に許可されたページのみを来場者へ提供する
2. While 現在のフェーズが開催前である, when 来場者が公開対象として許可されていないページの URL へ直接アクセスする, the 荒牧祭サイト shall HTTP ステータス 404 を返し、当該ページの内容を応答に一切含めない
3. The 荒牧祭サイト shall 開催前フェーズで公開するページの一覧を、単一の定義として保持する
4. When 新しいページが追加され、かつ公開対象として明示的に許可されていない, the 荒牧祭サイト shall 開催前フェーズにおいて当該ページを非公開として扱う
5. The 公開範囲の制御 shall 固定パスのページと動的パスのページ (一覧に対する個別詳細ページ、slug で解決される固定ページ等) の双方へ適用される
6. The 公開範囲の制御 shall 動的パスについて、ルートの形状単位ではなく、パスに与えられる個々の値単位で公開可否を判定する
7. While 現在のフェーズが開催前である, the 荒牧祭サイト shall 非公開ページへの導線 (ナビゲーション項目・本文中のリンク・一覧内のカード等) を来場者へ提示しない
8. While 現在のフェーズが開催中である, the 荒牧祭サイト shall すべてのページを来場者へ提供する
9. The 開催前フェーズの公開対象 shall 現行のヘッダー・フッターのナビゲーションおよび現行トップページ本体から到達できるページのうちトピックス詳細を除いたもの (トップ、お知らせ一覧、お知らせ詳細、アクセス、プライバシーポリシー等) を含み、その確定した一覧を design フェーズで定める

### Requirement 3: フェーズに応じたトップページの出し分け

**Objective:** As a 実行委員, I want フェーズに応じてトップページの内容が切り替わること, so that 開催前は告知中心、開催中は当日案内中心の表示を一度の切替で実現できる

#### Acceptance Criteria

1. While 現在のフェーズが開催前である, the 荒牧祭サイト shall 開催前向けのトップページを表示する
2. While 現在のフェーズが開催中である, the 荒牧祭サイト shall 開催中向けのトップページを表示する
3. When フェーズが切り替わる, the 荒牧祭サイト shall トップページの切り替えと公開範囲の切り替えを同時に適用し、両者が食い違う中間状態を生じさせない
4. Where 開催中向けのトップページが未実装である, the 荒牧祭サイト shall 開催中フェーズにおいても既存のトップページを表示し、エラーとしない

### Requirement 4: 開発者向けフェーズオーバーライド

**Objective:** As a 開発者, I want ソースコードのフェーズ定数を変更せずに任意のフェーズでサイトを閲覧したい, so that 開催中フェーズのページを来場者へ公開する前に確認できる

フェーズがビルド時に確定するため、本番・プレビュー・ローカルのいずれもデプロイ時点のフェーズで動作する。オーバーライドは開催中フェーズを事前確認する唯一の手段であり、本 spec において中核の要件である。

#### Acceptance Criteria

1. The 荒牧祭サイト shall ソースコード内のフェーズ定数を変更することなく、開発者自身の閲覧にのみ適用されるフェーズを指定する手段を提供する
2. When 開発者がオーバーライドでフェーズを指定する, the 荒牧祭サイト shall ソースコード内のフェーズ定数より指定されたフェーズを優先して適用する
3. While オーバーライドが有効である, the 荒牧祭サイト shall 指定されたフェーズの公開範囲とトップページ表示の双方を適用する
4. While オーバーライドが有効である, the 荒牧祭サイト shall 当該オーバーライドを指定した開発者の閲覧にのみ影響させ、他の閲覧者の表示を変更しない
5. The オーバーライド shall 追加のデプロイを要さずに適用および解除できる
6. If オーバーライドとして想定外の値が指定された, then the 荒牧祭サイト shall 当該指定を無視し、ソースコード内のフェーズ定数に基づいて動作する
7. If オーバーライドとして想定外の値が指定された, then the 荒牧祭サイト shall 来場者および開発者へエラーページを表示せず、通常の表示を継続する

### Requirement 5: オーバーライドの永続性と適用範囲

**Objective:** As a 開発者, I want 一度指定したフェーズがサイト全体で維持されること, so that ページを移動するたびに指定し直す必要がない

#### Acceptance Criteria

1. When 開発者がオーバーライドでフェーズを指定する, the 荒牧祭サイト shall 指定を行ったページだけでなく、同一サイト内のすべてのページへ当該フェーズを適用する
2. While オーバーライドが有効である, the 荒牧祭サイト shall ページ遷移・再読み込み・ブラウザの再起動をまたいで当該オーバーライドを維持する
3. The オーバーライド shall 開発者が別のフェーズへ切り替えるか解除操作を行うまで維持される
4. When 開発者がオーバーライドを解除する, the 荒牧祭サイト shall ソースコード内のフェーズ定数に基づく表示へ戻る

### Requirement 6: 開発用フェーズ切替 UI

**Objective:** As a 開発者, I want 画面上のボタンからフェーズを切り替えたい, so that URL の編集や開発者ツールの操作をせずに双方のフェーズを行き来できる

#### Acceptance Criteria

1. Where 開発用フェーズ切替 UI が有効である, the 荒牧祭サイト shall 画面の左下に、現在適用中のフェーズを示す常時表示の操作要素を描画する
2. When 開発者が当該操作要素を操作する, the 荒牧祭サイト shall 適用するフェーズを切り替え、切り替え後のフェーズで現在のページを再表示する
3. The 開発用フェーズ切替 UI shall 現在適用中のフェーズがソースコード内のフェーズ定数によるものかオーバーライドによるものかを判別できる表示を行う
4. The 開発用フェーズ切替 UI shall オーバーライドを解除する操作を提供する
5. The 開発用フェーズ切替 UI shall ページ本体のコンテンツの閲覧と操作を妨げない位置および大きさで表示する

### Requirement 7: 本番環境における開発用機能の非露出

**Objective:** As a 実行委員, I want 開発用のフェーズ切替手段が来場者へ一切露出しないこと, so that 来場者が未公開ページを閲覧したり開発用 UI を目にしたりしない

#### Acceptance Criteria

1. The 本番環境の荒牧祭サイト shall 開発用フェーズ切替 UI を描画しない
2. The 本番環境の荒牧祭サイト shall フェーズオーバーライドの指定を受け付けず、常にソースコード内のフェーズ定数に基づいて動作する
3. If 来場者が本番環境でオーバーライドを指定する操作を試みた, then the 本番環境の荒牧祭サイト shall 当該指定を無視し、ソースコード内のフェーズ定数に基づく表示を返す
4. The 本番ビルドの成果物 shall 開発用フェーズ切替 UI のコードを含まない
5. The 荒牧祭サイト shall 開発用フェーズ切替 UI とオーバーライドを、アクセス制限された環境 (ローカル開発環境およびアクセス制御されたプレビュー環境) においてのみ有効とする
6. The 荒牧祭サイト shall 本番相当の設定で開発用機能が無効であることを自動テストで検証する

### Requirement 8: 非公開ページの外部露出防止

**Objective:** As a 実行委員, I want 非公開ページが検索エンジンや SNS 上へ露出しないこと, so that 開催前に未完成のページが外部から発見されない

#### Acceptance Criteria

1. While 現在のフェーズが開催前である, when 非公開ページの URL が SNS 等で共有される, the 荒牧祭サイト shall 当該ページの内容を推測できるメタ情報 (タイトル・説明・画像) を応答に含めない
2. While 現在のフェーズが開催前である, the 荒牧祭サイト shall 非公開ページに対して、検索エンジンがインデックス対象としない応答を返す
3. The 荒牧祭サイト shall 非公開ページの外部露出防止を、robots.txt 等の追加の除外設定に依存せず、ページ応答そのものによって成立させる
4. When フェーズが開催中へ切り替わる, the 荒牧祭サイト shall それまで非公開であったページを通常の応答で返し、検索エンジンおよび SNS から到達可能にする

### Requirement 9: フェーズに連動する sitemap の提供

**Objective:** As a 実行委員, I want 公開中のページが sitemap で検索エンジンへ提示されること, so that 来場者が検索から必要な情報へ到達できる

> 本 spec が担う sitemap は開催前フェーズの公開対象を収録範囲とする。開催中フェーズでのみ公開されるページ (企画一覧・キャンパスマップ・トピックス等) の収録は `full-site-design` の責務とした。同 spec がページ構成と URL 構造を作り直すため、確定していない URL を先回りして収録対象に加えても手戻りになる。動的パスの収録をお知らせ詳細のみに限った理由と同じである。

#### Acceptance Criteria

1. The 荒牧祭サイト shall サイト内の公開ページを列挙した sitemap を提供する
2. While 現在のフェーズが開催前である, the sitemap shall 開催前フェーズで公開対象となっている固定パスと、公開済みのお知らせ詳細ページのみを収録する
3. The sitemap shall 現在のフェーズにおいて非公開であるページの URL を一切含めない
4. When フェーズ定数を変更したデプロイが完了する, the sitemap shall 新しいフェーズの公開対象を収録した内容へ更新される
5. Where 開催中フェーズでのみ公開されるページが存在する, the 荒牧祭サイト shall それらの URL を本 spec の sitemap 収録対象とせず、収録は `full-site-design` の責務とする
6. If sitemap の生成中に CMS からお知らせ一覧を取得できない, then the 荒牧祭サイト shall 固定パスのみを収録した sitemap を返し、sitemap の生成自体を失敗させない
