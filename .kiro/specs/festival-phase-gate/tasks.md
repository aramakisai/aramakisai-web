# Implementation Plan

- [ ] 1. フェーズ判定基盤の構築

- [x] 1.1 フェーズの語彙・ビルド時定数・開発用フラグを定義する
  - 開催前と開催中の 2 値のみを持つフェーズ型と、適用元 (ビルド時定数かオーバーライドか) を表す型を定義する
  - 現在のフェーズを決める単一のビルド時定数を置き、初期値を開催前とする。切替がこの 1 行の変更として PR の diff に現れる形を保つ
  - オーバーライド Cookie の名称を定数として定義し、他モジュールが Cookie 名を直書きしない状態にする
  - 開発用オーバーライドを有効にしてよいビルドかどうかの真偽値を、ビルド時にリテラルへ畳み込まれる形で定義する。ローカル開発は実行環境の判定で、それ以外は専用の公開環境変数の値でのみ有効化する
  - 環境変数集約モジュールを経由せず直接参照する理由 (集約モジュール経由では定数畳み込みが効かず、本番成果物から開発用コードを除去できないこと) をコード上のコメントに残し、規約からの逸脱をこのモジュール 1 箇所に閉じる
  - フェーズ型・ビルド時定数・Cookie 名・開発用フラグが単一モジュールから公開され、型チェックが通る状態になる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.6, 1.7, 1.8, 3.3, 7.5_

- [x] 1.2 公開対象一覧と公開可否判定を実装する
  - 開催前フェーズで公開するパスの唯一の定義を、ナビゲーション定義から独立した静的な列挙として持つ
  - 公開対象はトップ、お知らせ一覧、お知らせ詳細、アクセス、プライバシーポリシーの 5 つに確定させる
  - お知らせ詳細はルート単位で許可し、slug で解決される固定ページは値まで確定したパスのみを許可する非対称な表現を採る。前者は公開済み判定が既存の取得処理側にあり、後者はルート単位の許可が固定ページ全体を公開してしまうため
  - この非対称を 2 つの定数で表す。完全一致で判定する一覧 (トップ、お知らせ一覧、アクセス、プライバシーポリシー) と、前方一致で判定する前置詞の一覧 (お知らせ詳細) を分ける。単一の配列に混ぜると、要素が完全一致か前方一致かを型から読み取れず実装がぶれる
  - 指定フェーズにおけるパスの公開可否を判定する純粋関数を実装する。開催中フェーズでは常に公開と判定し、開催前フェーズでは完全一致の一覧に含まれるか前方一致の前置詞で始まるパスのみを公開と判定する
  - 一覧に載らないパスが開催前フェーズで必ず非公開になること、開催中フェーズが全パスを公開と判定することをユニットテストで検証する
  - 公開対象の各パス・一覧外のパス・許可外の slug・開催中フェーズの各条件でユニットテストが通る
  - _Requirements: 2.3, 2.5, 2.6, 2.9_

- [x] 1.3 実効フェーズの解決とナビ項目の絞り込みを実装する
  - Cookie 値から実効フェーズと適用元を解決する純粋関数を実装する。開発用フラグが偽のときは Cookie 値を参照する経路自体が存在しない形にする
  - Cookie 値が語彙に含まれないとき、例外を投げずビルド時定数へ落とす。Cookie は利用者が自由に書き換えられる入力であり、信頼境界での入力検証として扱う
  - ナビゲーション項目の配列を受け取り、指定フェーズで非公開となるリンク先を持つ項目を除去する関数を実装する。アンカー付きのパスを誤って除去しない
  - Cookie 未設定・妥当な値・不正な値・開発用フラグが偽の各条件で期待どおりのフェーズと適用元が返ることをユニットテストで検証する
  - 開発用フラグが偽のとき、いかなる Cookie 値を与えても常にビルド時定数のフェーズが返ることがテストで確認できる
  - _Requirements: 4.1, 4.2, 4.6, 4.7, 7.2, 7.3_

- [x] 2. (P) リクエスト経路上のゲートと 404 応答先を実装する
  - 実効フェーズを解決し、開催前フェーズで公開対象に含まれないパスへのリクエストを遮断するゲートをリクエスト経路上に追加する
  - 遮断時は、404 を返すだけの実在ルートへ内部的に書き換える。存在しないパスへの書き換えには既知の不具合報告があるため採らない
  - 書き換え先のルートは描画内容を持たず、既存の 404 画面がヘッダー・フッターを伴って描画される位置に置く。直接アクセスされても 404 を返すのみで副作用を持たない
  - 書き換えによって URL は変わらず、来場者には元の URL のまま 404 が表示される
  - ゲートの対象から静的アセット・フレームワーク内部パス・sitemap を除外する。sitemap はフェーズに応じた内容を自身で出力するためゲートを通さない
  - 除外の指定は design が定めた対象 (フレームワークの内部パス、favicon、sitemap、拡張子を持つ全パス) に従う。本番では静的アセットがそもそもゲートを経由しないが、ローカル開発では経由するため環境間で挙動を揃える目的で明示する
  - 書き換え先の URL はリクエスト URL を複製して経路部分のみを差し替え、クエリ文字列は破棄する。書き換え先はクエリを解釈せず、非公開パスのクエリを下流へ渡す経路を残さないため
  - ゲートは外部 I/O を持たず、CMS を呼ばない
  - 遮断された応答が、本来存在しないパスへの 404 と内容・ステータスともに区別できない状態になる
  - 公開パスを素通しし非公開パスを書き換えることをユニットテストで検証する
  - _Requirements: 1.5, 2.1, 2.2, 2.4, 2.8, 7.2, 7.3, 8.1, 8.2, 8.3, 8.4_
  - _Boundary: PhaseGate middleware, gated ルート_
  - _Depends: 1.2, 1.3_

- [x] 3. (P) フェーズに連動する sitemap を実装する
  - 開催前フェーズの公開対象となっている URL のみを収録する sitemap を追加する。収録対象は公開対象一覧から導出し、独自のパス一覧を持たない
  - 開催中フェーズでのみ公開されるページ (トピックス・企画一覧・キャンパスマップ等) は収録しない。公開対象一覧は開催前フェーズ用のものしか存在せず、開催中用の一覧をここで新設すると `full-site-design` がページ構成を作り直した時点で二重管理になる。収録は同 spec へ委ねる
  - 動的パスはお知らせ詳細のみを収録する。既存のお知らせ取得処理をそのまま再利用する。企画詳細とトピックス詳細は対応ページの URL 構造が未確定のため収録しない
  - URL の組み立ては基点とパスの結合を URL 生成に任せる。サイト URL の環境変数は末尾スラッシュの有無を規定していないため、文字列結合では二重スラッシュが生じうる
  - CMS からの取得に失敗した場合は固定パスのみを収録した sitemap を返し、エラー応答にしない。既存のお知らせ取得処理は失敗時に例外を投げるため、呼び出し側で捕捉する
  - 公開可否判定が真を返す URL のみが出力されることをユニットテストで検証する
  - 開催前フェーズの sitemap に非公開ページの URL が一切含まれないことがテストで確認できる
  - _Requirements: 9.1, 9.2, 9.3, 9.4, 9.5, 9.6_
  - _Boundary: PhaseSitemap_
  - _Depends: 1.2_

- [ ] 4. 開発用フェーズ切替 UI の実装と結線

- [x] 4.1 (P) フェーズ切替の操作要素を実装する
  - 画面左下に常時表示され、現在適用中のフェーズと、それがビルド時定数によるものかオーバーライドによるものかを判別できる操作要素を追加する
  - 操作によってフェーズを切り替え、切替後は現在のページを再取得して切替後のフェーズで描画し直す。クライアント側でフェーズに応じた表示を組み立てず、サーバ側の判定を唯一の真実とする
  - オーバーライドの解除操作を持ち、解除後はビルド時定数に基づく表示へ戻る
  - Cookie の書き込みと削除をクライアントから直接行い、専用の API 経路を設けない
  - Cookie はサイト全体を対象とし、長期の有効期限を与えてページ遷移・再読み込み・ブラウザ再起動をまたいで維持される
  - ページ本体のコンテンツの閲覧と操作を妨げない位置と大きさで表示される
  - 適用中フェーズと適用元の表示、切替、解除の各挙動がコンポーネントテストで確認できる
  - _Requirements: 4.3, 4.5, 5.1, 5.2, 5.3, 5.4, 6.1, 6.2, 6.3, 6.4, 6.5_
  - _Boundary: PhaseToggle_
  - _Depends: 1.1, 1.3_

- [x] 4.2 ルートレイアウトへ切替 UI を結線する
  - ルートレイアウトで実効フェーズを解決し、切替 UI へ渡す。全画面レイアウト配下のページにも表示されるようにする
  - ルートレイアウトは現状同期の Server Component であり、Cookie 取得が非同期 API であるため非同期関数へ変更する
  - 開発用フラグが偽のときは Cookie を読まずに描画を打ち切り、切替 UI を一切描画しない。短絡評価により Cookie を読む経路自体がビルド時に消える形にする
  - 開発用フラグが偽の条件でレイアウトを描画したとき、切替 UI が出力に現れないことをテストで検証する
  - _Requirements: 4.4, 7.1_
  - _Depends: 4.1_

- [ ] 5. 非公開ページへの導線の非提示

- [ ] 5.1 (P) ナビ項目を描画する全コンポーネントをフェーズで絞り込む
  - サイトレイアウトで実効フェーズを解決し、ナビ項目を描画するコンポーネントへ渡す。サイトレイアウトは現状同期の Server Component であり、Cookie 取得が非同期 API であるため非同期関数へ変更する
  - 対象はヘッダー (PC 用とモバイル用の 2 箇所)、フッター、そしてキャンパスマップのメニューボタンの 3 コンポーネントすべてとする。メニューボタンはヘッダーからナビ項目の配列を直接取り込んで描画しており、ここを外すと `full-site-design` が未公開ページをナビへ戻した時点でこのコンポーネントだけが非公開リンクを出し続ける
  - 受け取ったフェーズで各ナビ項目を絞り込み、現在のフェーズで非公開となるリンク先を持つ項目を提示しない
  - ナビゲーション項目の定義そのものは変更しない。定義の所有権は `full-site-design` にあり、本タスクは与えられた項目を絞り込む結線のみを行う
  - 既存のコンポーネントテストは対象コンポーネントを引数なしで呼び出しているため、フェーズを必須の引数にすると型エラーになる。あわせて更新する
  - 現行のナビ項目はすべて開催前フェーズの公開対象に含まれるため、この時点では表示が変化しない。絞り込みが機能するのは `full-site-design` が未公開ページをナビへ戻した時点である
  - 非公開のリンク先を持つ項目を与えたとき、開催前フェーズで 3 コンポーネントのいずれでもその項目が描画されないことをテストで検証する
  - _Requirements: 2.7_
  - _Boundary: ナビ項目を描画する 3 コンポーネントへの変更_
  - _Depends: 1.3_

- [x] 5.2 (P) 開催前フェーズでトップページのトピックス節を描画しない
  - トップページで実効フェーズを解決し、開催前フェーズではトピックス節を描画しない。開催中フェーズでは従来どおり描画する
  - あわせてトピックスの取得自体を止める。トップページ用のデータ取得処理はトピックスを含む全データを一括取得しており、描画だけを落とすと取得は毎リクエスト走り続ける。トップページは毎リクエスト動的に描画されるため、この無駄が恒常的に残る
  - 取得処理にフェーズを引数で渡し、開催前フェーズではトピックスを取得せず空の結果を返す。取得処理を項目ごとに分割する方式は採らない。呼び出し側が 1 箇所しかなく、分割は現時点で使い道のない自由度を増やすだけである
  - カードのリンクを外す方式は採らない。カードはタイトルと要約を表示するため、リンクを外しても非公開ページの内容の一部を提示し続けることになる
  - 開催中向けのトップページが未実装の現時点では、開催中フェーズでも既存のトップページを表示しエラーとしない
  - 開催前フェーズで描画したときトピックス節が出力に現れず、開催中フェーズでは現れることをテストで検証する
  - 開催前フェーズで描画したときトピックス取得が呼ばれないことをテストで検証する
  - _Requirements: 2.7, 3.1, 3.2, 3.4_
  - _Boundary: トップページのトピックス節、トップページ用データ取得処理_
  - _Depends: 1.3_

- [ ] 6. 本番環境における開発用機能の非露出の保証

- [ ] 6.1 開発用フラグの注入箇所を限定しワークフロー構造テストで検証する
  - 開発用フラグを、アクセス保護が確認できる配信先へデプロイするジョブのビルドステップのリテラルな環境変数ブロックにのみ追加する
  - シークレット管理基盤へは一切登録しない。これによりフラグが有効になる箇所がリポジトリ内の 1 行に限定され、本番環境へ誤って変数が追加される経路そのものが存在しなくなる
  - 既存のワークフロー構造テストの作法に従い、開発用フラグが当該ジョブにのみ現れ、検証ジョブ・プレビュー配信・本番配信のいずれにも現れないことを検証するテストを追加する
  - 判定はフラグの変数名そのもので行う。環境変数ブロックの有無では判定できない — 検証ジョブのビルドステップにもダミー値の環境変数ブロックが既に存在するため
  - PR プレビュー URL はホスト名ベースのアクセス制御の対象外であり保護されていないため、プレビュー配信では有効にしない
  - 追加したワークフロー構造テストが通り、フラグの注入箇所が機械的に固定される
  - _Requirements: 1.4, 7.5, 7.6_

- [ ] 6.2 本番相当ビルドの成果物に開発用コードが含まれないことを検証する
  - 開発用フラグを与えずにビルドした成果物を走査し、切替 UI 固有の文字列 (Cookie 名等) が含まれないことを検証するテストを追加する
  - 走査対象は実行基盤へ配信される出力ディレクトリとする。フレームワークの中間出力のみを走査すると、配信前の再バンドルの結果を見落とす
  - 既定のテストコマンドはビルドを行わないため、このテストはその対象に含めない。ビルドしてから成果物を走査する独立したスクリプトとし、CI では検証ジョブとは別のステップから呼ぶ。ローカルでも同一コマンドで再現できるようにする
  - 成果物からの除去はバンドラの定数畳み込みと dead code elimination に依存するため、実測で確認する
  - 走査テストが失敗した場合は、除去方式をあらためて設計する。動的読み込みへの切り替えは解にならない。初期バンドルからの遅延分割であって成果物ディレクトリからの排除ではなく、分割後のチャンクに文字列が残るため走査テストは通らない。実効性があるのはフラグが偽のビルドで当該モジュールをエントリから外す方式である
  - 本番相当の設定でビルドした成果物に切替 UI のコードが含まれないことが、自動テストで機械的に確認できる
  - _Requirements: 7.4, 7.6_
  - _Depends: 4.2_

- [ ] 7. 構造テストと実機検証

- [ ] 7.1 ルートと公開対象一覧の整合を構造テストで担保する
  - アプリのルートを列挙する既存の仕組みを再利用し、各ルートが宣言済みの分類のいずれかに属することを検証する。未分類のルートが現れたら失敗させる
  - 分類は 2 値では足りない。完全一致で公開・ルート単位で公開・値単位で一部が公開・意図的な非公開の 4 種を設ける
  - 4 種目が要るのは、slug で解決される固定ページのルートがどちらにも収まらないためである。ルートパターン自体は公開対象一覧に載らないが、アクセスとプライバシーポリシーという公開値をこのルートが解決している。意図的な非公開に分類すると事実と矛盾し、公開に分類すると固定ページ全件の公開を意味してしまう
  - ゲートの書き換え先ルートを意図的な非公開として宣言する
  - ナビ項目を描画する全コンポーネントのリンク先がすべて開催前フェーズの公開対象に含まれることを検証し、開催前フェーズで死んだリンクが出ないことを保証する
  - 新しいページを追加して公開対象一覧にも非公開宣言にも登録しなかった場合に、テストが失敗する状態になる
  - _Requirements: 2.4, 2.7_
  - _Depends: 1.2, 2_

- [ ] 7.2 フェーズごとの応答を実機で検証する
  - 実行環境によって検証できる範囲が二分される。既存の E2E ジョブは接続先を PR プレビュー URL に固定しており、そのビルドには開発用フラグが入らない。オーバーライドが効くことの検証は CI では原理的に実行できない
  - **CI で実行する (開発用フラグ無効のビルドが対象)**
  - 開催前フェーズで公開対象のページが 200 を返し、非公開のページが 404 を返すことを検証する。書き換え経由の 404 が実行基盤上で実際に 404 ステータスを返すことの確認を兼ねる
  - 非公開ページの応答が、本来存在しないパスへの応答と同一の内容であることを検証する
  - 通常ページの描画が壊れていないことを確認し、ゲート対象の除外指定に漏れがないことを担保する
  - オーバーライドを設定しても非公開ページが 404 のままであることを検証する。フラグ無効のビルドを相手にするため、この検証はプレビュー環境でこそ意味を持つ
  - **ローカルで手動実行する (CI 対象外)**
  - オーバーライドを設定した状態で非公開ページが閲覧でき、ページ遷移をまたいで維持されることを検証する
  - 開発用の切替 UI が描画され、切替と解除が機能することを確認する
  - これらは開発用フラグが有効なビルドを要する。該当するのはローカル開発環境と開発用の配信先のみで、PR ごとに回せる対象がない。専用ジョブを設ける価値は現時点では無く、実装時とオーバーライド周辺の変更時に手動で確認する
  - CI 対象の検証が E2E テストとして通り、ローカル対象の検証手順が記録される
  - _Requirements: 2.1, 2.2, 2.8, 5.1, 5.2, 7.3, 8.1, 8.2, 8.4_
  - _Depends: 2, 4.1, 4.2_
