# Implementation Plan

- [ ] 1. 時刻表の抜き出しと定期更新
- [x] 1.1 ODPT の時刻表 GTFS から対象停留所の発車を抜き出して JSON を生成する
  - zip 展開と CSV 読み取りのライブラリを開発用依存に加え、手動実行用のコマンドを登録する
  - CKAN のデータセットページ (HTML) から全版の日付を得て zip を取得し、`feed_info.txt` の有効期間が今日より前に終わった版を除く。版が 1 つも読み取れない・有効期間が無いときは失敗する
  - 群馬大学荒牧・前橋自動車教習所前(2 停留所 3 ID)の乗車できる停車だけを抜き出し、行先(停留所の行先を優先)・経由(全角括弧の中)・方面(`direction_id` 1 = 前橋、0 = 渋川)・系統(路線名の先頭)を付ける
  - 対象の発車を持つ運行日区分についてだけ、曜日・期間と例外日を書き出す
  - 対象停留所が見つからない、方面が 0/1 以外、時刻表の記号表に無い経由が現れた場合は失敗し、既存の JSON を書き換えない
  - 出力の並び順を固定し、取得日時は版の内容が変わったときだけ更新する(同じ入力から 2 回実行して差分が出ない)
  - 小さな GTFS の断片を使ったユニットテストで、乗車不可の除外・停留所の行先の優先・経由の分離・方面の対応・運行日の書き出し・想定外の経由での失敗を確かめ、すべて通る
  - 実際に実行して生成した時刻表 JSON がリポジトリに置かれている
  - _Requirements: 1.1, 1.3, 1.5, 4.3_

- [ ] 1.2 時刻表を毎日更新して PR を作るワークフローを追加する
  - 毎日 05:00 JST と手動実行で抜き出しを実行し、時刻表 JSON に差分があるときだけ dev 向けの更新ブランチに commit して PR を作る。同じブランチの PR が開いていれば push で更新する
  - PR の作成には CMS の CI のリリース処理と同じ GitHub App のトークンを使い、作られた PR でフロントエンドの CI が起動するようにする
  - PR 本文に追加・削除された版と有効期間を書く
  - 抜き出しが失敗したらワークフローが失敗し、PR を作らない
  - 手動実行で、差分が無いときは PR が作られず、差分があるときは dev 向けの PR ができる
  - _Requirements: 1.5_

- [x] 2. 発車予定の計算とリアルタイム情報の取得
- [x] 2.1 (P) 日付から版と運行日を決め、その日の発車一覧を返す
  - 日付を含む有効期間の版のうち、開始日が最も新しい版を選ぶ。無ければ発車一覧を空にする
  - 曜日・期間で有効な運行日区分に例外日の追加・除外を反映する
  - ユニットテストで、期間の境界・2 版が重なる日・祝日の例外・年末年始、2026-11-14 が土曜・2026-11-15 が日祝の区分になることを確かめ、すべて通る
  - _Requirements: 1.2, 1.3, 4.4_
  - _Boundary: bus-timetable_

- [x] 2.2 (P) GTFS-RT の必要な項目だけを読むデコーダを作る
  - 生成時刻、便ごとの停車順と遅れ(到着の遅れ、無ければ発車の遅れ、どちらも無ければ 0)、車両の便・現在の停車順・状態を読み、知らない項目は読み飛ばす
  - 負の遅れを正しく読み、壊れた入力では例外を投げる
  - 2026-10-30 に取得した実データ(便ごとの遅れ・車両)を fixture にしたユニットテストで、便 ID・停車順・遅れ・生成時刻を読めること、負の遅れを読めることを確かめ、すべて通る
  - _Requirements: 2.2_
  - _Boundary: gtfs-realtime_

- [x] 2.3 リアルタイム情報をブラウザから定期取得するフックを作る
  - 既存の定期取得の仕組みで、遅れと車両の 2 フィードを ODPT から直接 30 秒ごとに並行して取得する。間隔を短くする引数は持たない
  - 画面が隠れている間は取得しない
  - 取得・デコードに失敗したフィードは前回の値を捨てて空として扱い、一度も取得できていなければ「情報なし」を返す
  - 生成時刻は 2 フィードの古い方を返す
  - ユニットテストで、失敗時に空になること・生成時刻の選び方を確かめ、すべて通る
  - _Requirements: 2.1, 2.4, 2.6, 2.7_

- [x] 2.4 方面ごとの次の便を、時刻表・リアルタイム情報・現在時刻から求める
  - 設計の「次の便の決定」のフローどおりに発車済みを判定する(車両の情報がある便は対象停留所を出るまで残す)
  - 遅れがあれば発車予定に遅れを加え、遅れ分数(早着は 0)と、遅れを反映したか時刻表どおりかの区別を返す
  - リアルタイム情報の生成時刻が 5 分以上前なら使わない。同じ便が 2 停留所に停まるときは発車済みでない最初の停車を採る
  - 発車予定までの分数は切り上げ・0 以上とし、方面の順は前橋駅方面・渋川駅方面とする
  - 既存のサイネージ用の計算はサイネージを切り替える 4.4 まで残し、型チェックが通る状態を保つ
  - ユニットテストで、車両が対象停留所を過ぎた/過ぎていない、遅れの情報だけ、リアルタイム情報なし、5 分以上古い、全便発車済みの各場合を確かめ、すべて通る
  - _Requirements: 2.2, 2.3, 2.4, 2.5, 3.2, 3.4, 5.2, 5.4, 5.5_
  - _Depends: 2.1, 2.2_

- [x] 3. (P) サイト設定にアクセスタブを追加し、固定ページ access の内容を移す

  - サイト設定のタブと項目の一覧のテストを更新し、型を再生成する
  - ローカルの CMS でマイグレーションを適用すると、サイト設定のアクセスタブに固定ページ `access` と同じ本文・埋め込みと現行の案内文が入っており、CMS のテストと型チェックが通る
