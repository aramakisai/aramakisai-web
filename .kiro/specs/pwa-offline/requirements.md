# Requirements Document

## Project Description (Input)

公式サイトを PWA 化し、会場で電波が細る状況でも構内マップとタイムテーブルを閲覧できるようにする。祭当日はキャンパスに人が集中して回線が実質使えなくなる時間帯があり、その状況でこそ地図と時間割が必要になる。

### 対象範囲

オフラインで閲覧できるようにするもの:

- 構内マップ (`campus-map`) — 地図タイル、エリアポリゴン、エリアごとの出展物リスト
- タイムテーブル (`timetable-page`)
- 企画一覧・企画詳細 (`exhibition-pages`) のテキスト情報とサムネイル

オフラインでは提供しないもの:

- CMS の管理画面
- 最新情報の取得を伴う機能 (お知らせの新着取得など)

### 前提

- 会場が荒牧キャンパス 1 か所に閉じているため、事前に配信対象を確定できる。`campus-map` が確定したタイル資産はズーム 17〜19 の約 1323 枚・約 7.7MB (2026-09-19 時点の見積もり。生成後に実測値へ更新する)。ズーム 15〜16 のタイルは生成対象に含まれない。
- 地図タイルは `campus-map` が OpenStreetMap のデータから自前でレンダリングし、`/map-tiles/{z}/{x}/{y}.png` として自前配信する。OpenStreetMap の公式タイルサーバは Tile Usage Policy 第 4 節で事前取得とオフライン利用の双方を禁じているため、公式タイルをキャッシュする選択肢は取らない。
- 企画・エリア・タイムテーブルのデータは件数が小さく、画像を除けば数十 KB に収まる。

### 検討事項

- キャッシュの鮮度をどう扱うか。企画情報は当日直前まで変わるため、オフライン時に表示している内容がいつ時点のものかを来場者に伝える必要がある。
- オンライン復帰時の更新方法。バックグラウンド同期を行うか、次回訪問時の取得に任せるか。
- 画像の扱い。サムネイルまでキャッシュすると容量が増えるため、オフライン時はプレースホルダに落とす選択肢がある。
- インストールを促すかどうか。促す場合、どの画面でいつ出すか。WebKit は Service Worker の登録とキャッシュを「7 日間サイトの利用がない場合に破棄する」対象に含めており、ホーム画面に追加した Web App はこの対象から外れる。祭の数日前に地図を用意しておく使い方を想定するなら、ホーム画面への追加を促すことが実質の前提条件になる。
- 容量そのものは制約にならない。WebKit のストレージポリシーはオリジンあたりディスク全体の最大 60% を上限としており、ホーム画面に追加した Web App もブラウザと同じ枠を持つ。約 7.7MB は誤差の範囲。

### 関連 spec

- **本 spec が依存するもの**
  - `campus-map`: 自前配信する地図タイルの資産と、その配信形式 (個別タイルか単一ファイルか) に依存する。先に `campus-map` を実装する
  - `timetable-page`: オフライン対象に含めるため、ページの実装が先に必要
  - `exhibition-pages`: 同上
- **本 spec に依存するもの**
  - `digital-signage`: サイネージ端末も回線断に耐える必要があり、本 spec のキャッシュ戦略を流用しうる

### 未確定事項

- `@opennextjs/cloudflare` で Service Worker を配信できるか。Cloudflare Workers 上の Next.js で Service Worker の登録とスコープがどう扱われるか未確認であり、これが成立しない場合は本 spec の前提が崩れる
- 約 1323 枚の個別タイルを Cache API へ入れる際の所要時間と失敗時の扱い。`campus-map` が配信形式を個別 PNG に確定したため単一ファイル形式の検討は不要だが、`addAll()` に 1300 件超を一度に渡した場合の挙動と、途中で失敗したときの再開方法は確認が要る
- オフライン対応の範囲をページ単位で切るか、データ単位で切るか
- iOS Safari の PWA 制約 (ストレージ容量、キャッシュの破棄タイミング) が想定容量に耐えるか
