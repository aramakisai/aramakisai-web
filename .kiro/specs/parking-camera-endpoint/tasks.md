# Implementation Plan

2つのリポジトリとInfisicalにまたがる。各タスクの題名の先頭に、作業する場所(`aramakisai-web`・`aramakisai-infra`・`Infisical`)を書く。PRはdevへ出し、devからmainへ上げる。

**本番への反映順**: design.mdの「Migration Strategy」のとおり、次の順で反映する。

1. Infisical prodへの`GEMINI_API_KEY`の登録(タスク1)
2. `aramakisai-infra`の`cms-secrets`への2つのキーの追加と同期(タスク2)
3. CMSのイメージの反映(タスク10.1)
4. 管理画面でのカメラの登録・トークンの発行と、撮影端末への書き込み(タスク10.2)
5. frontendの反映(タスク10.3)

タスク2は`aramakisai-web`の作業(タスク3〜9)と並行して進めてよい。

**開発サーバー**: `make dev`・`make signage-dev`・`make cms-worktree`経由でだけ起動し、`pnpm dev`・`next dev`・`-p`/`--port`を直接使わない。ポートは自分で選ばない。Claudeが起動するときは`run_in_background`を使い、他のセッションや人間が立てたサーバーを止めない。ポート3000には触らない。CMSのスキーマを変えるため、CMSを伴う検証は`make cms-worktree`と`make dev CMS=worktree`(または`make signage-dev CMS=worktree`)で行い、共有の`make cms`は使わない。ローカルのCMSに必要な秘密値はInfisical prodから注入してよい。

**UIの実装と確認**: 公開ページの駐車場の行とサイネージの駐車場画面は、Figmaファイル`0kWDqHsLr6xE8b4FFgR1Zx`の指定したnode-idをFigma MCPで実測してから実装し、Figmaを正とする。Figmaに無い状態や値を足さない。UIの確認は実ブラウザで寸法を測って行い、vitestの通過だけで完了扱いにしない。実ブラウザでの確認の後は必ずブラウザを閉じ、判断に使ったスクリーンショットのフルパスを記録する。見た目を変えるコード(タスク5.1・8.2・8.3)のコミットは、タスク9の実ブラウザでの確認の後に行う。

- [x] 3. aramakisai-web: CMSの判定・受信が使う純粋な処理を作る
- [x] 3.1 (P) デバイス用トークンの生成とハッシュを作る
  - 32バイトの乱数をbase64urlにした43文字のトークンを作り、SHA-256(hex)のハッシュを求める。乱数とハッシュは`node:crypto`で行う
  - 受信時の照合は`Authorization`の値のハッシュで引く前提とし、ソルトや低速ハッシュは使わない
  - 発行値が43文字のbase64urlで、同じ値が同じハッシュになる単体テストが通る
  - _Requirements: 1.2, 1.6_
  - _Boundary: ParkingCameraToken_

- [x] 3.2 (P) 写り具合から露出補正値を決める処理を作る
  - 露出の起点(写り具合、判定した画像を撮ったときの露出補正値、その撮影時刻)から次の露出補正値を決める。起点が無い、または起点の撮影から30分を過ぎていれば値なしにする
  - `too_dark`で+1、`too_bright`で-1、`ok`・`color_cast`で据え置きにし、-2〜+2に収める
  - 起点なし・30分超で値なし、各写り具合の増減、+2・-2での頭打ちの単体テストが通る
  - _Requirements: 1.8, 1.9, 4.11_
  - _Boundary: ParkingExposure_

- [x] 3.3 (P) 端末状態のヘッダーを読む処理を作る
  - `X-Device-Rssi`・`X-Device-Uptime`・`X-Device-Reset-Reason`・`X-Device-Failures`・`X-Device-Firmware`を、design.mdの「受信エンドポイントの取り決め」の形と範囲で読み、外れる項目だけを値なしにする。例外を投げない
  - 5項目すべて正しい値、欠落、小数・範囲外のRSSI、33字の再起動理由、65字・非ASCIIの版でその項目だけ値なしになる単体テストが通る
  - _Requirements: 8.1, 8.2_
  - _Boundary: ParkingDeviceStatus_

- [x] 3.4 (P) サイト設定に監視時間を足し、監視時間内かの判定を作る
  - `site_settings`に`parking_monitor`グループ(`start`・`end`、`HH:mm`、日本時間、既定`09:00`・`17:30`)を足し、`HH:mm`の形と`start < end`を検証する。実行委員が管理画面のサイト設定で変えられる
  - 日本時間の時刻が`start ≤ t ≤ end`なら監視時間内(両端を含む)とする判定を作り、受信(撮影時刻)・稼働監視・公開側(現在時刻)で同じ扱いにする
  - 日本時間8:55・17:35は外、9:00・17:30は内で、設定値を変えるとそれに従う単体テストが通る
  - _Requirements: 4.13_
  - _Boundary: site_settings_

- [x] 3.5 (P) モデルごとの呼び出し回数の計数を作る
  - 上限は`gemma-4-26b-a4b-it`・`gemma-4-31b-it`が30RPM・14,400RPD、`gemini-3.1-flash-lite`が15RPM・500RPD。1分は直近60秒の呼び出し時刻で、1日は太平洋時間の日付で数える。呼び直しも1回に数え、TPMは数えない
  - 枠があれば1回分を確保し、429を受けたモデルを指定の時刻まで使わない。計数はワーカーのプロセスのメモリだけに持つ
  - 1分の上限で止まり60秒後に戻る、太平洋時間の日付の変わり目で1日の計数が戻る、休止中は取れない単体テストが通る
  - _Requirements: 4.5_
  - _Boundary: ParkingJudgeRate_

- [x] 3.6 Gemini APIで画像を判定する処理を作る
  - `generateContent`を`fetch`で直接呼び、`x-goog-api-key`ヘッダーでキーを渡す。プロンプト・応答スキーマ・写り具合だけの判定の形はdesign.mdの「ParkingJudge」のとおりにする
  - モデルは`gemma-4-26b-a4b-it` → `gemma-4-31b-it` → `gemini-3.1-flash-lite`の順。1回の呼び出しは20秒で打ち切る。500・503・打ち切り・通信失敗・応答の形が不正は同じモデルで3回まで(2秒、4秒待つ)、429は呼び直さずそのモデルを60秒休ませて次へ、その他の4xxは次へ。呼び出しの前に計数の枠を取り、取れなければ次へ
  - 呼び直しの前に対象の画像がまだ最新かを確かめ、最新でなければ打ち切る。`congestion: unknown`はモデルを切り替えずに判定失敗の結果として返す。`image_quality`だけが不正なら写り具合を値なしで返す
  - 一度も呼び出せなかったときは見送り、呼び出したが通らなかったときはモデルごとの最後の応答コードを並べた要約付きの失敗を返す
  - `fetch`を差し替えた単体テストで、500を2回のあと成功、26Bが3回500で31Bへ、429で即座に次へ、全モデル失敗で失敗と応答コードの要約、`unknown`で切り替えない、`image_quality`だけ不正で写り具合が値なし、最新でなくなったら打ち切りが通る
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.9, 4.11, 4.12_
  - _Depends: 3.5_

- [x] 5.2 撮影端末の受信エンドポイントを作る
  - ルートのエンドポイント`/api/parking-ingest`を置き、design.mdの「受信エンドポイントの取り決め」のリクエスト・応答のとおりに動かす。認証は本文を読む前に行い、`Content-Length`で1MiBを超える本文を読む前に拒否し、無いときも1MiBを超えた時点で読むのをやめる
  - 検証は認証 → 大きさ → 形式(先頭3バイトと`sharp`のメタデータ) → `X-Exposure` → `X-Captured-At`(2分を超える未来・10分を超える過去は拒否、ちょうどは受け付ける) → 監視時間の順に行い、失敗したら保存もジョブ登録もしない。監視時間外は200の`{}`を返し、画像・露出の起点・最後の撮影時刻を変えない
  - 認証に成功したら、以降の検証の結果に関わらず、カメラの端末状態を今回のヘッダーと受信時刻で全項目書き直す
  - 画像を推測できない乱数のファイル名で保存し、割り当て先は保存時点のカメラの割り当てを写す。保存のあとカメラの最後の撮影時刻を更新し、同じカメラの古い画像を削除する(削除の失敗は応答に反映しない)
  - 撮影時刻の枠(`floor(撮影時刻 / 枠の長さ)`、枠の長さは`PARKING_JUDGE_WINDOW_SECONDS`、既定300秒)を、最後に判定を積んだ枠が空か今回より小さいときだけ条件付きで更新し、更新できたときだけ判定ジョブを積む。取れなければ画像を見送り(`same_window`)にする
  - 応答の露出補正値は、その時点でカメラが持つ露出の起点から決める。割り当ての有無で分岐しない
  - 検証の単体テストで、`X-Exposure`の範囲外・小数・欠落で400、`X-Captured-At`の欠落・非整数・2分超の未来・10分超の過去で400(境目ちょうどは受け付ける)、`Content-Type`違い・先頭バイト違いで415、1MiB超で413が通る
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.7, 1.8, 1.9, 1.10, 1.11, 1.12, 3.1, 3.2, 4.5, 4.6, 8.1, 8.2_

- [x] 5.3 判定ジョブを作る
  - ジョブ`judgeParkingSnapshot`(入力は画像のIDとJPEGのbase64、`retries: 0`)を`jobs.tasks`に足す
  - 画像が無ければ何もせず終える。割り当て先があれば混雑と写り具合、無ければ写り具合だけを判定させる。`GEMINI_API_KEY`が未設定なら`not_configured`の失敗を記録し、起動時に1度だけ警告を出す
  - 結果を画像に記録する(見送りは`rate_limited`、打ち切りは何もしない)。写り具合が有効で、画像の撮影時刻が露出の起点より新しければ起点を更新する
  - 混雑の判定に成功し、画像を引き直して割り当て先が残っていれば、その駐車場の空き状況を判定結果で更新する。値が同じでも更新して更新時刻を新しくし、手入力の値も上書きする。空き状況の作成・削除はしない。写り具合は空き状況の判断に使わない
  - 判定の失敗・見送りはカメラID・画像ID・理由をwarnでログに出し、成功・トークン・APIキーはログに出さない
  - Geminiの呼び出しを差し替えた単体テストで、成功で空き状況が更新され、失敗・見送りで空き状況が変わらず、割り当て先が無い画像で空き状況を更新しないことが通る
  - _Requirements: 4.6, 4.7, 4.8, 4.10, 4.12, 5.1, 5.2, 5.3, 5.4, 5.5, 5.7, 5.8_

- [x] 5.4 カメラの稼働監視の定期ジョブを作る
  - ジョブ`checkParkingCameras`を毎分0秒の`schedule`で足す。`PARKING_CAMERA_DISCORD_WEBHOOK_URL`が未設定なら何もせず、起動時に1度だけ警告を出す
  - 通知の対象期間(`site_settings.event_days`の開始日時を日本時間の暦日にした、開催初日の7日前から開催最終日まで)の外、監視時間外、`event_days`が空のときは何もしない。割り当て先のあるカメラだけを対象にする
  - 基準時刻を最後の撮影時刻と今日の監視開始時刻の遅い方にし、通知中の停止が無く15分以上届いていなければ停止を送り、成功したら停止を通知した時刻を書く。通知中の停止があり、それより新しい撮影があれば復旧を送り、成功したら印を消す。送信に失敗したら印を変えず次の分に送り直す
  - 本文と送信の形(5秒で打ち切り、`allowed_mentions`は空)はdesign.mdの「CheckParkingCamerasTask」のとおりにし、値の無い端末状態は「不明」、一度も受け取っていなければ「端末状態: 未受信」にする
  - 時刻を差し替えた単体テストで、9:14に当日の画像なしで通知しない・9:15で停止、最後の撮影10:00で10:14は通知しない・10:15で停止、通知済みなら10:16に再送しない、10:20の画像で復旧を1回送り印が消える、17:31以降・未割り当てのカメラは通知しない、対象期間の境目(7日前は対象、8日前は対象外、最終日は対象、翌日は対象外、`event_days`が空なら対象外)、送信失敗で印を書かず次で送り直す、本文の各項目と「不明」が通る
  - _Requirements: 8.4, 8.5, 8.6, 8.7, 8.8, 8.9, 8.10_
